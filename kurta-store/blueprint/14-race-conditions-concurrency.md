# 14 — Race Conditions & Concurrency

A cross-cutting reference, not a build step: every concurrency race this blueprint deliberately handles, where, how, and — since not every race is equally likely or equally bad — how seriously to take each one. The authoritative implementations live in the numbered files; this is the audit view.

## Every race, catalogued

| Race | Where it can happen | Mechanism | File | Likelihood / severity |
|---|---|---|---|---|
| Last-unit double charge | Two buyers checking out the same variant simultaneously | Stock reserved (`stock_reservations`, 15-min TTL) *before* the payment gateway is ever called; availability computed under `SELECT ... FOR UPDATE` | `05` | High-traffic launches/drops make this common; fully handled, don't weaken it |
| Concurrent stock decrement at order-commit | A reservation-less internal/admin order racing a customer order for the same variant | Guarded `UPDATE ... WHERE stock >= qty`, checks `affectedRows === 0` to detect a stock change that slipped in between read and write | `05` | Rare in practice (admin orders are infrequent), but cheap to guard so it's guarded anyway |
| Order-number counter collision | Two checkouts completing in the same instant | The `counters` row is locked `FOR UPDATE` *inside* the same transaction as the rest of order creation, so a rolled-back order releases its number instead of burning a gap | `05` | Guaranteed to happen eventually at any real order volume; this is the one race that's structurally certain, not just possible |
| Duplicate order from a retried/double-submitted payment | A webhook retry or a client double-submitting the verify call after a slow response | `orders.paymentGatewayId` unique index is the DB-level backstop; the app-level idempotency check runs first and returns the existing order instead of erroring | `05` | Webhook retries are common with most payment gateways — treat this as expected, not exceptional |
| Coupon over-redemption past `maxUses`/`perUserLimit` | Two checkouts using the same coupon simultaneously, at or near the limit | Coupon row locked `FOR UPDATE`; `coupon_usage_coupon_user_unique` index is the DB-level backstop for `perUserLimit = 1` specifically | `05` | Low-probability (requires hitting the exact limit at the exact instant) but high-consequence if unguarded (real revenue loss from a stackable discount), so fully locked |
| Duplicate Delhivery shipment push | An admin double-clicking "push to courier", or a retry after a slow response | Checks `orders.delhiveryOrderId` is unset *before* calling the courier at all — skips the call entirely if already pushed | `07` | Easy to trigger by accident (impatient double-click); consequence is a second real-world waybill for one parcel, which is expensive to unwind manually — worth the explicit guard |
| Concurrent cold-cache image resize | Many simultaneous first-requests for a never-before-resized width | In-memory `Map<string, Promise<Buffer>>` de-dupes by cache-path key so only one resize actually runs | `04` | Common right after a new product image upload goes live to real traffic; low severity (worst case is a wasted CPU cycle, not a correctness bug) — see `12-scalability-performance.md` for why this de-dup is per-process, not global |
| Two pending OTPs for one email | A user requesting a new code before the old one expires | `otps.email` is unique; the send flow overwrites the existing row rather than creating a second one | `02`/`03` | Common (users regularly hit "resend"), fully handled |
| Reservation cleanup lag | The `release-stock-reservations` cron hasn't run recently | Every availability read filters `WHERE expiresAt > NOW()` itself — an uncollected expired row can never wrongly block a sale, regardless of whether the cleanup cron ran on schedule | `02` | Not really a race so much as a designed invariant: correctness never depends on the cron's timing at all |

## General principles

- **A DB-level unique index is the ultimate backstop against check-then-write (TOCTOU) races.** An app-level "check it's not already used, then insert" always has a gap between the check and the write; a unique index makes the *second* write fail outright instead of silently succeeding into an inconsistent state. Every race above that says "backstop" is leaning on this.
- **Scope `FOR UPDATE` locks as narrowly as possible** — lock the specific variant/coupon/counter rows actually being touched, never a whole table. A wide lock would serialize unrelated checkouts against each other for no reason; seeing this pattern get wider over time (e.g. someone "simplifying" by locking the whole `product_size_variants` table) is a regression, not a cleanup.
- **A guarded `UPDATE ... WHERE <condition>` with an `affectedRows` check is a lighter-weight alternative to `FOR UPDATE`** when you don't need a full transaction boundary around the check — useful for the reservation-less fallback stock decrement.
- **Ask "what happens if two of these run at the exact same instant?" for every new mutation that touches a limited or shared resource** (stock, counters, usage caps, anything with a max/limit). Default to a DB-enforced answer, not an app-level check with a timing gap — this is the discipline the whole checkout flow is built on, and it should extend to any future feature that adds a new limited resource.

## A currently-undocumented race, found by inspection

`design_configs` (file `02`) is a single-row table where every homepage section is a whole JSON blob column, and the `PATCH` route (file `06`) does a partial update — but only at the *column* level, not within a column. Two admins editing **different top-level sections** concurrently (one editing `heroContent` while another edits `stats`) is safe — each writes only the key it touched. But two admins editing **different items within the same array field** concurrently — e.g. one reordering hero banners while another edits the USP items' text, both touching `heroBanners` — isn't actually the failure case; the real failure case is two admins **both editing the same array field** (say, both adding/reordering entries in `heroBanners`) in overlapping edits: whichever `PATCH` lands second overwrites the *entire array* the other admin was working from, silently dropping the first admin's change. There's no optimistic-concurrency check (no version/`updatedAt` comparison) anywhere in this path.

This is a genuine gap, not a hypothetical — but it's worth being explicit that it's an **accepted trade-off, not an oversight**: the CMS is admin-only, low-concurrency (realistically one or two people editing the homepage at a time), and the cost of a lost edit is "redo the change," not "customer gets charged twice." Document it as accepted rather than leaving it silently unhandled. If multiple admins editing the homepage concurrently ever becomes a real workflow, the fix is straightforward: compare the row's `updatedAt` at PATCH time against the value the editor loaded, and reject with a "this was changed by someone else, reload and retry" error on mismatch (optimistic locking) — not full field-level merging, which would be substantial added complexity for a rare scenario.

## Verification

- Fire two parallel `create-razorpay-order` requests for the last unit of a variant — exactly one succeeds, the other gets a clean 409 before any payment attempt. File `05`.
- Fire two parallel checkouts using the same near-limit coupon — confirm at most `maxUses` (or `perUserLimit`) redemptions are ever recorded, never one more.
- Double-click the admin "push to courier" button on an already-pushed order — confirm the second call makes no outbound courier request and returns `alreadyPushed: true`.
- Request the same never-before-resized image width from two concurrent clients on a cold cache — confirm (via a log line or counter) only one resize actually executes.
- Manually backdate a `stock_reservations` row's `expiresAt` into the past without running the cleanup cron, then attempt a fresh purchase of that stock — confirm the reservation is correctly ignored as expired.
